**Décisions clés :** (1) **Fortify** retenu sur Breeze — le frontend jQuery/AJAX imposé par le cours rend le scaffolding Blade de Breeze inutile, alors que Fortify est headless par conception et expose des points d'extension (redirection par rôle, rate limiting nommé) directement utiles ici. (2) **PDF** (barryvdh/laravel-dompdf) retenu sur HTML imprimable — un fichier binaire figé renforce l'immuabilité exigée par la Constitution Principe III, sans dépendance à un binaire externe. (3) Auth par **session + CSRF**, pas de préfixe `/api/v1/` ni Sanctum — application monolithique same-origin, un préfixe API découplé serait une sur-ingénierie (YAGNI). (4) `devis.client_id` rendu **NOT NULL** — résolution d'une tension interne entre FOUNDATION §10.2 (nullable) et §11.1 (vérification email avant validation) : la composition vit en session tant que le compte n'est pas vérifié, la ligne `devis` n'existe qu'après. (5) Seeders de valeurs tarifaires par défaut pour couvrir le point de friction "onboarding tarifaire vide" (§11.4) sans créer de User Story ni logique dédiée.
**Selfdoubt appliqué :** 7 affirmations auditées (protocole appliqué car 3+ composants impactés sur Breeze/Fortify, PDF/HTML, et le schéma `devis.client_id`) — 4 marquées ⚠️ Probable (hedge-to-verify ratio 0,57), concentrées sur des choix de conception comblant des vides ou tensions internes du FOUNDATION (PDF vs HTML reste un jugement, pas une exigence explicite ; portabilité de dompdf dépend d'un hébergement pas encore choisi ; résolution client_id NOT NULL est une interprétation, pas une donnée tranchée). Aucune incertitude sur les principes de sécurité eux-mêmes (Policies, hachage, CSRF, isolation), qui sont une application directe de la Constitution.
**Impact :** livre à l'UI/UX (#3) un référentiel technique complet (structure de vues à prévoir pour Fortify headless, état "brouillon" du devis géré en session avant persistance, valeurs tarifaires par défaut déjà en base, format PDF pour le téléchargement) et au Backend (#4) une organisation de code (Domain/Actions/Infrastructure, Policies) directement implémentable.
**Alerte agent suivant :** (1) Fortify = zéro vue fournie, toutes les pages auth/profil sont à concevoir de zéro en HTML/jQuery — à intégrer dans le design ; (2) prévoir 3 redirections post-connexion différenciées par rôle dès la maquette ; (3) le tunnel de devis doit gérer un état "brouillon" sans ID persistant tant que la validation n'a pas eu lieu (pas de compte encore) ; (4) le point priorisation P0/P1/P2 du PO reste non tranché par l'Architecture — à valider par mentalyas avant le séquencement UI/backend ; (5) format PDF retenu → prévoir un simple lien de téléchargement, pas de prévisualisation HTML custom.
